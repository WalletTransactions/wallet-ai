# Design

## Context

Мотивация — proposal.md. Опирается на незаархивированный `add-statement-import`
(код в `main`, `3427c66`).

Что есть сейчас:
- Строка импорта (`statement_row`) знает `dir: expense | income | transfer`,
  но не знает знак: проверка (`verify_row`) видит знак суммы в исходнике и
  использует его только для смены `income`/`expense`.
- Готовые операции строятся только для расходов: `acc_fr` — кошелёк импорта,
  `acc_to` — категория. Всё, что не расход, лежит в `income_transfer` и
  считается закрытым.
- Правила — `merchant_rule (user_id, pattern) → category_uuid`, растут из
  правки категории.
- Сверка (`fetch_ops`) берёт из `GET /api/reports/operations` только `kind:
  expense` своего кошелька.
- `pattern_of` выбрасывает числа из 4+ цифр, поэтому «Внутренний перевод на
  договор 5107173931» и «…на договор 5630778099» дают один pattern «ВНУТРЕННИЙ
  ПЕРЕВОД НА ДОГОВОР».

Возможности соседних сервисов:
- wallet-api: перевод в одной валюте — одна операция кошелёк → кошелёк. Две
  ноги через системный счёт Transfer и `operation_link` нужны только для
  разных валют.
- wallet-report: в `operations` у перевода `kind: transfer`, `from_uuid`,
  `to_uuid`.

Инвариант wallet-ai: сервис ничего не пишет в кошелёк, запись делает клиент.

## Goals / Non-Goals

**Goals:**
- Перевод из выписки записывается одной операцией, повторный импорт второй
  стороны его не задваивает.
- Пользователь выбирает второй кошелёк один раз на номер договора или тип
  операции, дальше правило.
- Ненужные строки («Проценты на остаток», переводы между своими счетами,
  которые не хотят видеть) убираются одной кнопкой навсегда.

**Non-Goals:**
- Разные валюты, доходы, создание кошельков — proposal.
- Сведение пар между двумя незаписанными импортами: сверка с журналом после
  записи первого импорта даёт тот же результат без связи импортов между
  собой.
- LLM в этом change не участвует: ни новых заданий, ни правок промптов.

## Decisions

### T1. Направление перевода — `flow`, из знака исходника
`verify_row` уже находит число из строки, совпавшее с суммой модели, вместе с
его знаком. Знак сохраняется в результате проверки, и строке-переводу
ставится `flow: out` при «−» и `flow: in` при «+». Разбор по колонкам берёт
знак колонки суммы. Знака нет — `flow: null`, выбирает пользователь.

Отвергнуто: просить направление у модели (`dir: transfer_out/in`). Это
правка схемы и промпта, токены, а знак в выписках почти всегда есть, и код
читает его без ошибок.

### T2. Одна таблица правил вместо `merchant_rule`
`statement_rule`:
- `id`, `user_id`;
- `key_kind` (`pattern` | `ref` | `type`), `key`;
- `action` (`category` | `transfer` | `ignore`), `target_uuid` (категория,
  кошелёк или NULL);
- `updated_at`;
- `UNIQUE (user_id, key_kind, key)`.

Миграция `000002` переносит `merchant_rule` в `statement_rule` (`pattern`,
`category`) и удаляет старую таблицу. Repo отдаёт список правил пользователя.
Применяет их одна функция (порядок `type` → `ref` → `pattern`, T4) и при
завершении разбора, и при правках.

Отвергнуто: три таблицы под три действия. Тогда «одно правило на ключ»
пришлось бы держать кодом, а `GET /statement-rules` склеивать из трёх
запросов.

### T3. `ref` — последние 4 цифры номера из исходника, а не из описания
Для PDF и текста `ref` берётся из строк-источников. Модель пересказывает
описание и иногда теряет номер договора: на ТБанке было «Внутренний перевод
на договор 3841» вместо «…5107173931». Берётся самое длинное число из 6+
цифр подряд; пробелы разрывают число, поэтому суммы «120 000.00» не
подходят. Для строк по колонкам `ref` ищется только в колонке описания:
другие колонки — остаток, курс, id операции банка.

- 4 цифры — как банки сами маскируют номера («*3931»). Шанс совпадения у
  двух договоров одного человека мал, а полный номер не хранится
  (приватность).
- Под правило `ref` попадают и номера телефонов («+79997711452» → «1452»),
  но правило `transfer` применяется только к строкам-переводам, а
  «Внешний перевод по номеру телефона» — расход.

Отвергнуто: ключ «pattern + ref» одним правилом. Правило `ref` →
кошелёк — это по сути «номер договора принадлежит кошельку». Оно верно для
любого текста вокруг номера, и английская выписка с «contract 8226738737»
пользуется тем же правилом, что русская.

### T4. Порядок применения: `type` → `ref` → `pattern`
Тип операции CSV точнее всего: «ATM Withdrawal» — всегда снятие. `ref`
различает договоры с одинаковым текстом. `pattern` — запасной ключ для строк
без номера («Перевод себе»). Ручной выбор пользователя (`counter_source:
manual`, `category_source: manual`) правила не перекрывают.

Обучение (`PATCH`) сохраняет правило по самому точному ключу, который есть у
строки: `ref`, иначе `type`, иначе `pattern`. Для `transfer` `ref` раньше
`type`: у банкомата ref нет, у перевода между договорами есть. Для `ignore`
ключ — `type` или `pattern`, но не `ref`: игнор «всего, где упомянут договор
X» слишком широк.

### T5. Новые поля строки
`statement_row`:
- `flow` (`in` | `out` | NULL);
- `counter_wallet_uuid` (NULL);
- `counter_source` (`rule` | `manual` | NULL);
- `source_type` — тип операции из CSV, NULL у PDF и текста;
- `ref` (4 цифры или NULL) — считается один раз при сохранении строки, чтобы
  не разбирать исходник на каждый `GET`.

`decision` получает значение `ignore`, `rule_ignored` — флаг игнора по
правилу (решение пользователя `include` его перекрывает).

### T6. Группы и готовые операции
`group_of`:
- `ignored`, если `decision: ignore` или игнор по правилу без `include`;
- `income` — для `dir: income`;
- для `dir: transfer` — `transfer` с `transfer_reason`, если нет кошелька,
  нет `flow` или валюты разные; иначе те же ветки, что у расхода (`check`,
  `exists`, `imported`, `possible_duplicate`, `ready`), без
  `needs_category`.

Валюта второго кошелька берётся из `accounts_snapshot` импорта, как у
кошелька импорта. Готовая операция перевода — по T1: `out` — кошелёк импорта
→ второй, `in` — второй → кошелёк импорта.

Отпечаток (`fingerprint`, D8 импорта) у перевода тот же, что у любой строки;
`dir` в нём — `transfer`. `op_uuid` двух импортов одного перевода разные,
поэтому от задвоения защищает сверка (T7), а не `uuid`.

### T7. Сверка переводов с журналом
`fetch_ops` дополнительно берёт `kind: transfer`, где `from_uuid` или `to_uuid`
— кошелёк импорта, и сохраняет пару `from`/`to`. Строка-перевод сравнивается
только с переводами той же пары и направления. Сумма — в валюте кошелька:
перевод в одной валюте, `amount` совпадает с обеих сторон. Дата ±1 день, одна
операция — одна строка, как у расходов. Запрос тот же, период тот же, нового
трафика в wallet-report нет.

### T8. API
- `PATCH /api/ai/imports/{id}/rows`:
  - новые поля строки `counter_wallet_uuid`, `flow`;
  - `decision: ignore`;
  - ошибки `unknown_wallet`, `same_wallet`, `bad_flow`;
  - `counter_wallet_uuid` у не-перевода — 400 `not_transfer`.
- Ответ импорта:
  - у строки `flow`, `counter_wallet_uuid`, `counter_source`,
    `transfer_reason`;
  - группы `income`, `transfer`, `ignored` вместо `income_transfer`.
- `GET /api/ai/statement-rules`, `DELETE /api/ai/statement-rules/{id}` — под
  тем же `ai:use`, через гейтвей `/api/ai/*`.

Правки в других сервисах:
- wallet-gateway — нет, префикс `/api/ai/` уже проксируется;
- wallet-web — change `add-ai-statement-import` (группы, выбор кошелька,
  «Игнорировать всегда», страница правил);
- wallet-infra, google-auth, wallet-common, wallet-api, wallet-report — нет.

### T9. Нагрузка на GPU
Нет: правила, сверка и группы — код и SQL. На строку — один проход по
правилам пользователя (единицы-десятки), на импорт — тот же один постраничный
запрос в wallet-report.

## Risks / Trade-offs

- [Два договора с одинаковыми последними 4 цифрами] → правило `ref` подставит
  не тот кошелёк. Видно в строке (`counter_source: rule`), правится выбором и
  перезаписывает правило.
- [Модель поставила `transfer` расходу с текстом «перевод» — например
  «Внешний перевод по номеру телефона» другу] → `transfer_words` профиля
  такие строки не трогают. Если всё же `transfer` без кошелька, строка в
  группе `transfer`, не записывается, видна пользователю.
- [Перевод записан вручную до импорта с другой датой (±2+ дня)] → сверка не
  найдёт, перевод задвоится. То же, что у расходов, и тот же выход: решение
  `duplicate`.
- [BREAKING группы для клиента] → веб импорта ещё не написан. Group
  `income_transfer` убирается сразу, без переходного периода.
- [Правило `ignore` по `pattern` спрячет нужную операцию] → `ignored` —
  отдельная видимая группа с числом строк, правило удаляется через
  `DELETE /statement-rules/{id}`.

## Migration Plan

1. Миграция `000002_statement_rules`:
   - `CREATE TABLE statement_rule`;
   - `INSERT … SELECT` из `merchant_rule`;
   - `DROP TABLE merchant_rule`;
   - `ALTER TABLE statement_row ADD COLUMN …` (T5).

   Down — обратный перенос правил `category`/`pattern` и `DROP` новых колонок.
2. Выкат wallet-ai одним образом. Открытые импорты в `ready` после выката:
   - старые переводы получают `flow: null`;
   - `ref` и `source_type` пересчитываются при первом открытии из
     `source_text`, если пусты.
3. Откат — предыдущий образ и down-миграция. Правила `transfer` и `ignore`
   теряются, категорийные остаются.

## Open Questions

- Запоминать номер договора самого импорта из шапки («Номер договора:
  8226738737») как `ref` → кошелёк импорта. Тогда во второй выписке перевод на
  этот договор найдёт кошелёк без единого выбора. Это улучшение подстановки,
  а не новое поведение, его можно добавить после MVP.
- Переводы между кошельками в разных валютах (Wirex EUR ↔ EUROC, обмен в
  банке) — отдельный change с двумя ногами и `operation_link`.
